## Критические (jank скролла)

### 1. `queueMarkRead` дёргает стор на КАЖДОМ scroll-событии → перерисовка всего чата
`stores/messengerStore.ts:232` — в `queueMarkRead` `useMessengerStore.setState(...)` вызывается
**безусловно**, независимо от того, продвинулась ли read-линия:

```ts
export function queueMarkRead(conversationId, messageId, sentAt) {
  const existing = pendingReadLine.get(conversationId);
  if (isLaterReceipt(receipt, existing)) pendingReadLine.set(...); // guard есть, но…
  ...
  useMessengerStore.setState((s) => ({                    // ← БЕЗУСЛОВНО
    conversations: s.conversations.map((c) => c.id === conversationId ? { ...c, unread_count: 0 } : c),
  }));
}
```

`queueMarkRead` вызывается из `MessageList.reportVisibleReads()` **на каждое событие scroll**
(и в layout-effect после каждого изменения списка). Каждый вызов создаёт НОВЫЙ объект
conversation → `selectSelectedConversation` возвращает новый identity → `ChatView`
перерисовывается → `renderMessage` (useCallback с dep `[conversation, …]`) получает новый
identity → `MessageList` (memo) ломается по пропу `renderMessage` → **полный ре-рендер
виртуального списка на каждое движение скролла**. На длинных диалогах это основной источник
заметного статтера при прокрутке.

Фикс: ставить `setState` только когда `unread_count` реально меняется (или когда
read-линия продвинулась: `isLaterReceipt` уже считает — использовать его же для раннего
выхода). Не трогать `conversations`, если ничего не изменилось.

### 2. Жёсткое прилипание к низу: `AT_BOTTOM_SLACK = 80` + clamp при любом изменении
`MessageList.tsx:28` — `AT_BOTTOM_SLACK = 80`; `MessageList.tsx:245` — состояние «у низа»,
когда до конца < 80px; `MessageList.tsx:334`:

```ts
if (isAtBottomRef.current) {
  const maxScrollTop = Math.max(0, el.scrollHeight - el.clientHeight);
  if (Math.abs(el.scrollTop - maxScrollTop) > 1) el.scrollTop = maxScrollTop;
  return;
}
```

Layout-effect срабатывает на каждое изменение `[totalSize, messages, keyboardInset, …]`.
Пока пользователь в зоне 80px от низа — **любое** изменение (приход сообщения, коррекция
измерения, ресайз) жёстко защёлкивает скролл на самый низ. Это и есть «странные подкрутки»
и ощущение, что список «тянет вниз» при прокрутке вниз: дошёл до 80px — и тебя доснимает.

Фикс: уменьшить slack (до ~4–8px, как у Telegram), и прилипать только когда реально пришёл
новый контент, а не на любое перестроение; не хардкодить scrollTop, а разрешать оверскролл
пользователя.

### 3. Гонка: «перекидывает вниз» при медленном скролле вверх из-за зоны 80px
Следствие #2: пользователь начинает листать вверх от самого низа. Пока он в пределах 80px,
`isAtBottomRef.current === true`. В этот момент приходит WS-сообщение → `messages`
меняется → pin-effect срабатывает → `el.scrollTop = maxScrollTop` — пользователя
**выдёргивает обратно вниз** посреди его жеста. Ощущается как «перекинуть может вниз».

Фикс: при касании/поинтер-дауне немедленно снимать пин (`pointerdown`/`touchstart` → сброс
`isAtBottomRef` после реального движения), а не ждать первого scroll-события; см. также #2.

### 4. `addMessage` / `syncMessages`: полная пересортировка массива сообщений на каждое событие
`stores/messengerStore.ts` — `addMessage`: `[...s.messages, finalMessage].sort(sent_at)`;
`syncMessages`: merge + полный `sort`; `loadMoreMessages`: merge + `sort`. На каждое
WS-сообщение и на каждый реконнект пересоздаётся весь массив и пересортировывается
O(n log n). Плюс:
- часовые перекосы: сообщение с `sent_at` раньше текущего последнего вставляется в середину
  списка → виртуальные окна сдвигаются → якорь корректируется → «дёрг» даже при чтении истории;
- любые правки/приходы меняют identity массива → эффекты `MessageList` (`messages` в deps)
  перезапускаются.

Фикс: не сортировать весь массив — вставлять в конец, если `sent_at >= last` (обычный
случай), и лишь изредка «досортировывать»; хранить сообщения в Map/упорядоченной структуре.

### 5. Дёрганье при заходе: многостадийный рендер + каскад измерений
- `selectConversation` (`messengerStore.ts`) сбрасывает `messages: []` → `MessageList`
  возвращает `null` → `ChatView` показывает loader → из IndexedDB приходит кэш → список
  монтируется (новый virtualizer, каскад `measureElement`) → приходит сеть → массив
  заменяется. Каждый переход — отдельный layout-pass и clamp к низу → «мигает/дёргается
  при заходе».
- `MessageBubble.tsx` (useLayoutEffect + ResizeObserver): измеряет кол-во строк и
  переключает `is-compact`/`is-multiline` — у multiline меняется `padding-bottom: 22px`
  (`messenger.css`). На 50 сообщениях начальной загрузки это каскад последовательных
  коррекций высоты → `totalSize` меняется много раз → пин/якорь каждый раз подстраивается →
  видимое дрожание.
- `MessageContent.tsx`/`attachmentMedia.ts`: у картинок без meta бокс резервируется с
  fallback-пропорцией 4:3 (фото) / 16:9 (видео), после загрузки `rememberMeasuredRatio`
  меняет `aspectRatio` → бокс РЕЗАЙЗИТСЯ → рефлоу → пин/якорь коррекция (прыжок).
  Комментарий в коде прямо говорит «the box corrects once on first load» — это и есть прыжок.

Фикс: монтировать список один раз и подменять данные без стадии `[]` (показывать loader
поверх списка, а не вместо него); замерять высоту пузыря заранее (в estimate) или
отложить компакт/мультилайн до стабильного состояния; для картинок без meta — резервировать
реальный бокс через ThumbHash/пропорции из S3 (или хотя бы не менять размер после load,
а маскировать/обрезáть).

### 6. `scrollToBottom({ behavior: "smooth" })` — долгая анимация и борьба с новыми сообщениями
`MessageList.tsx:425` — императивный `scrollToBottom` использует smooth-скролл. Вызывается
из `ChatView.handleSend` (`ChatView.tsx`, `requestAnimationFrame(() => scrollToBottom())`)
**всегда** после отправки, даже если пользователь читал историю (комментарий в коде — это
намеренно, но UX-сомнительно). Проблемы:
- smooth по тысячам пикселей = длинная анимация; приход новых сообщений во время неё
  пересчитывает `maxScrollTop` → скролл «плавает», а на мобиле внутри touch-scroller
  smooth-скролл дёргается;
- пользователя выдёргивает из чтения истории (ещё одна «подкрутка»).
- Тест `MessageList.test.tsx:291` завязан на `behavior: "smooth"` — при смене на instant
  обновить.

Фикс: instant (`scrollTop = max`) при отправке; smooth оставить только для FAB-кнопки
и то с короткой дистанцией; не уводить из истории, если пользователь скроллил вверх
(показывать «новое сообщение» пилюлей, как Telegram).

### 7. Estimate высоты не совпадает с реальной для широких картинок
`MessageList.tsx` `estimateMessageHeight`: `boxWidth = Math.min(420, 480 * ratio)`, а реальный
`getAttachmentDisplayStyle` (fitToViewport) капит `maxWidth: 640`. Для широких изображений
оценка меньше реального → `measureElement` коррекция → drift. Плюс `__SHARE__`-карточки
оцениваются фиксированно 430px, реальная высота другая → та же коррекция.

Фикс: синхронизировать константы (единый источник: 640/420), оценивать share-карточку по
контенту (есть/нет превью-картинки).

## Высокие (поведение)

### 8. Restore-якорь: мгновенный «телепорт» + охота за якорем
`MessageList.tsx` — при возврате в чат `restoreAnchorRef` восстанавливает сохранённую
позицию мгновенным `el.scrollTop = target` (layout-effect), а если якоря нет в загруженных
сообщениях — цикл `loadMoreMessages` (по 50 шт.) до его появления. На медленной сети это:
телепорт при открытии (визуальный прыжок) + серия запросов истории, во время которых
позиция прыгает при каждом препенде.

Фикс: плавный/невидимый ресторе (показывать лоадер до готовности якоря, затем один
переход); ограничить охоту одним-двумя запросами с фолбэком на низ.

### 9. `captureAnchor` = null у самого верха → прыжок при препенде истории
`MessageList.tsx` `handleScroll`: если пользователь доскроллил до верха, `captureAnchor`
может вернуть `null` (нет элемента, пересекающего верхнюю кромку) → `anchorRef.current = null`
→ при препенде истории layout-effect нечего корректировать → контент под сдвигом. Видимый
прыжок при чтении самого старого.

Фикс: если якорь null и пользователь у верхнего края — сохранять позицию «scrollTop=0»
и явно держать её при препенде.

### 10. Per-frame ресайз от клавиатуры → пин/якорь на каждый кадр
`lib/mobileKeyboard.ts` `startGeometryFollow` обновляет `--app-vh`/`--kb-inset` каждый кадр
во время анимации клавиатуры → `MessageList` (dep `keyboardInset`) перезапускает
pin/anchor-effect каждый кадр → `el.scrollTop` переписывается каждый кадр. На десктопе
`keyboardInset` константа — ок; на мобиле это участвует в «дыхании» списка при открытии
клавиатуры. В сочетании с #2 (зона 80px) может дёргать.

Фикс: во время keyboard-анимации не трогать якорь/пин (клавиатура меняет только высоту
вьюпорта — пин к низу работает сам), либо сглаживать в самом скроллере.

### 11. `renderMessage` дорогое: `messages.find` на каждое цитируемое сообщение
`ChatView.tsx` `renderMessage`: для каждого сообщения с `parent_message_id` выполняется
`messages.find(...)` — O(n) на каждое. При 1000+ сообщениях и ре-рендерах из #1 это заметно.

Фикс: пре-индексировать `Map<id, MessageView>` один раз на массив.

## Средние / прочее

### 12. `updateConversationFromWs` пересортировывает ВЕСЬ список диалогов на каждое WS-сообщение
`messengerStore.ts` — `updatedConversations.sort(...)` на каждый `new_chat_message` → вся
`ConversationList` перерисовывается. На больших списках + частых сообщениях лишняя работа.
(Виртуализация списка диалогов включена только >20 элементов.)

### 13. `loadReceipts` создаёт новый `Map` → ChatView ре-рендер
Каждый `loadReceipts` (WS `read_receipt`, реконнект, открытие чата) кладёт новый `Map` →
`receipts` selector меняет identity → `ChatView` + все пузыри с рецептами перерисовываются.
Скорее всего ок, но на частых `read_receipt` — лишние ре-рендеры.

### 14. Состояние «у низа» и FAB
`isAtBottom` переключается только в `handleScroll`; при появлении «N новых сообщений» +
FAB, если сообщение пришло, пока юзер у низа — пузыри анимируются `bubble-in` (transform —
ок, layout не трогают). Но если юзер у низа и приходят несколько сообщений подряд — каждая
анимация перезапускает compositing; при слабых устройствах это заметно. Можно ограничить
анимацию только последним сообщением.

### 15. Мобильная компоновка: скрытие шапки AppLayout при открытом чате
`MessengerView.tsx` — на мобиле при открытом чате вешается `messenger-mobile-chat-active`
(прячет шапку) → сдвиг компоновки при каждом открытии чата (задумано, но может ощущаться
как прыжок; проверить на реальном устройстве).

### 16. `MessengerView` ресайз сайдбара: `setState` на каждый `mousemove`
Ожидаемо, но при перетаскивании на каждый пиксель — React-ре-рендер всей сетки
(`gridTemplateColumns`). На слабых машинах дёргается сам ресайз. Можно переписать на
CSS-переменную (без ре-рендера).

### 17. WS-события не батчатся
`websocket.ts` эмитит каждое сообщение отдельно; при реконнекте-шторме (много
`new_chat_message`) каждый эвент = отдельный `setState` + пересортировка (#4). Реконнект
плюс-минус прикрыт `syncMessages` (один дельта-фетч), но если сервер отдал пропущенное
пачкой — события идут по одному. Рассмотреть микро-батчинг (rAF/макротаск).

## Что уже хорошо (не ломать при переработке)

- Якорная стабилизация (anchor message + offset) — правильная идея, работает при препендах.
- Резервирование бокса под медиа по aspect-ratio — почти устраняет рефлоу картинок (кроме #5/#7).
- `overscroll-behavior-y: contain`, `scrollbar-gutter: stable`, `overflow-anchor: none`.
- Read-линия (один рецепт на пасс) и батчинг delivered/read — хорошая схема, чинится только #1.
- `messageLoadGeneration`/`loadMoreRequestGeneration` — защита от пересечений при смене чата.
- Мобильная клавиатура (`--app-vh`, `--kb-inset`, scroll-to-dismiss) — проработано глубоко.

## Приоритетный план переработки (порядок)

1. **#1** — убрать безусловный `setState` из `queueMarkRead` (самый большой выигрыш на скролле).
2. **#2+#3** — переработать пин к низу: узкая зона, снятие пина по `pointerdown`, прилипание
   только при реальном приходе контента.
3. **#5** — одностадийный заход в чат (не мигать `[]`→кэш→сеть; loader поверх списка),
   устранить каскад измерений пузырей и ресайз боксов картинок.
4. **#4** — вставка в конец без пересортировки; мап-индекс сообщений.
5. **#6** — instant-скролл при отправке; не выдёргивать из истории.
6. **#8/#9/#10** — ресторе якоря без телепорта; edge-кейсы верха; клавиатурный кадр.
7. **#11–#17** — производительность рендера и мелочи.

## Требование к результату
«Самое плавное в мире» = 0 запросов/сет-стейтов на скролл, 0 layout-сдвигов без контента,
0 программных скроллов во время пользовательского жеста. После каждого пункта — замер на
реальном устройстве (Chrome DevTools Performance + мобильный с эмуляцией 60fps).
